# bt-rearm 蓝牙布防

替不布防的安卓蓝牙栈,给已配对的 BLE 设备挂上后台自动回连。

## 它解决的问题

红魔平板 5 Pro(RedMagicOS 11.5 / Android 16)上,已配对的蓝牙低功耗手柄
关机再开机后**不会自动连回**:手柄持续广播可连接报文,系统一次连接尝试都不
发起,只能手动去设置里点一下那台设备。同一台平板上的罗技鼠标却一切正常,
所以机制是有的,只是不给这台手柄用。

抓包证据(btsnoop,2026-08-22):

- 手柄以配对记录中相同的地址连续广播 272 次,类型为 `CONNECTABLE+scannable`;
- 同一时段主机零次 `LE Create Connection`;
- 已排除:配对由谁创建、第三方 App 是否在场、蓝牙权限、"输入设备"策略开关。

## 原理

一开始走的是 `connectGatt(autoConnect = true)`:给目标设备挂一个后台连接客户端,
设备一广播链路就被拉起。链路确实能拉起来,但**系统不会因此接管**它 —— 设置里
照旧显示未连接,手柄照旧不能用。应用建的是自己的 GATT 链路,和系统的 HID 输入
服务是两回事。

让系统真正接管的动作是 `BluetoothDevice.connect()`,设置里点「连接」走的就是它。
它要 `BLUETOOTH_PRIVILEGED` 与 `MODIFY_PHONE_STATE`,两者都是签名/特权级权限,
普通应用申请不到也授不了。以下路径均已真机证伪:

| 尝试 | 结果 |
|---|---|
| 反射调 `BluetoothDevice.connect()` | 方法拿得到,系统服务端拒绝:缺 `MODIFY_PHONE_STATE` |
| HID_HOST profile 代理的 `connect(device)` | 被隐藏 API 名单拦下 |
| 配对记录残缺(缺 HID 服务 UUID / 类型不对) | 手柄记录正常,与能回连的鼠标一致 |
| 手柄广播地址与配对记录不符 | 地址分毫不差 |
| HID 连接策略被设成「禁止」 | 策略就是「允许」 |
| `fetchUuidsWithSdp()` 借系统 PhonePolicy 自行发起 | 触发送达,但那条分支只在策略「未知」时执行 |

shell 用户恰好握有这两个权限。Shizuku 能把一个进程拉起在 shell 身份下,应用把
连接请求送过去执行,系统便如常接管。所以应用做的是:

1. 列出已配对设备,点一台即开始布防;
2. 扫到它的广播、且系统没连它时,请 shell 身份的服务调用系统的连接接口;
3. 布防名单存在 SharedPreferences 里,下次启动自动恢复;
4. 前台服务把进程钉住,免得布防随进程被冻结而失效;
5. 自动重连走不通时弹通知喊人 —— 蓝牙关着、Shizuku 没就绪、或者设备断开
   已久重试无果(多半是手柄关机了,只有人能按那个键)。

Shizuku 未运行或未授权时退回自建链路,应用仍可用,只是换不来系统接管。

不需要 root,不修改系统,不碰配对记录。

### 前置条件

装 [Shizuku](https://shizuku.rikka.app/) 并启动它(无线调试或连电脑 adb),
首次运行时在弹窗里允许本应用使用 Shizuku。平板重启后 Shizuku 需要重新启动。

## 构建

工具链走 Nix(Android SDK 34 / NDK r27 / JDK 17 / cargo-ndk):

```sh
nix-shell Android.nix
just build      # cargo-ndk 编 .so + gradle 打 APK
just run        # 装到设备并跟日志
```

界面是 Slint,入口是 `NativeActivity` 加载的 cdylib;布防决策在 Rust 的 `engine`
模块里(有单元测试,不碰安卓 API),蓝牙那半边必须是 Java(BLE 的回调类是抽象类,
JNI 无法从 Rust 实现),两侧靠 JNI 相连。

## 两个要分开的问题

手柄的毛病其实是两件事,前期排查一度把它们搅在一起,这里先拆开:

- **为什么会断** —— 玩几分钟必掉一次,这是根本困扰。
- **断了之后回连要多久** —— 掉了要 3 秒以上才接回。

下面分别写。每条结论都标注是**实测**、**推断**还是**未测**;凡是后来发现说重了
的,原地更正,不抹掉 —— 这份文档的用处一半在于记下哪些弯路不必再走。

## 回连要多久:测到哪、没测到哪

链路断开(HCI 0x08 监督超时)到 **ACL 重新建立**,拆成四段实测:

| 段 | 优化前 | 优化后 | 归属 |
|---|---|---|---|
| 断开 → 开始扫描 | 518 ms | **30 ms** | 本应用 |
| 扫描 → 收到第一条广播 | — | 1466–3031 ms | 手柄 |
| 收到广播 → 发出连接 | — | 118 ms | Shizuku 跨进程调用 |
| 发出连接 → ACL 建立 | 2218 ms | **136–865 ms** | 系统蓝牙栈 |
| **合计(到 ACL)** | **3095 ms** | **3100–3361 ms** | |

主机侧的开销从约 2.7 秒压到 0.15 秒,分段都有实测支撑。但六次测量的总时长
分别是 3095、3282、3137、3361、3100、3321 毫秒 —— **看不出任何下降趋势**。
每砍掉一段,「等手柄开始广播」那一段就涨回来填上。

**这张表的终点是 ACL 建立,不是「手柄可用」——两者不是一回事,差值未测。**
ACL 起来只是链路通了,手柄真正能用还要等系统的 HID profile 接管完成。这段
滞后是已知的:引擎里 `SETTLE_MS = 30_000` 那个稳定窗口存在的理由,注释写的
就是「输入设备列表要等 HID profile 完全起来才转真,中间有几秒空窗」。也就是说
真实的用户感知时长是 `3.2 秒 + HID 接管`,而 HID 接管这段我从没打过时间戳。
如果它是一到两秒,合计正好落到体感的「5 秒以上」——**体感没错,是这张表把
终点画早了。**(补测这一段需要给 `dumpsys input` 里手柄出现的时刻打时间戳,
待有设备时做。)

### 这一段为什么压不动

扫描不是瓶颈,有硬证据。系统日志里扫描参数是 `160 / 160` 扫描单位,即间隔
100 毫秒、窗口 100 毫秒 —— 窗口等于间隔就是接收机全程在听,而且
`scanModeApp 2 scanModeUsed 2` 说明系统没有因为应用在后台把模式降级。也就是说
那两三秒里我们确实一直竖着耳朵,对面没在喊。

那「对面没在喊的 1.5–3 秒」到底是什么,现有数据分不清,有两种读法:

1. 手柄的监督计时器比平板晚了这么久才到期,它更晚才认定链路已死、才进广播态;
2. 两边同时判死,但手柄固件从断开到重新广播有个固定的重启延迟。

**这两种读法用现有日志无法区分**,所以只能说「回连时长被手柄重新广播的时机
卡住,主机侧够不着」,不能像本文档早先版本那样断定成「手柄的 3 秒监督超时」——
那是把读法一当成了唯一解。这个区别在下一节还要用到:读法二是对称的,不含任何
「谁先谁后」的信息。

## 为什么每几分钟断一次:证据能推到哪

这是核心问题,也是最容易凭直觉下错结论的地方。先把**确凿的事实**摆出来,再看
它们各自到底允许推出什么。

**事实(实测):**

- 掉线全是 HCI `0x08` 监督超时,即**连续三秒一个包都没成功交换**(`timeout=300`)。
  所以真凶必须能造成「连续三秒静默」,偶尔丢几个包不算。这道门槛淘汰掉很多嫌疑。
- 同一台平板上配对的罗技鼠标(也是 BLE)**从不掉线**;手柄五到十分钟一断。
- 掉线发生在**握着玩**的时候;间隔是 5–10 分钟,**不固定**。
- 连接参数每约 24 秒重协商一次,13 分钟内被改 47 次、44 次由手柄发起,在
  `interval=9`(11.25 ms)与 `interval=30`(37.5 ms)之间来回。
- WiFi 工作在 5 GHz。

### 鼠标为什么不断:这不是「平板没问题」的证据

最容易下错的一步:「鼠标好,所以不是平板的问题」。方向反了。

鼠标和手柄共享一切物理层 —— 同一个射频、同一个坞、同一套 ROM。它俩命运不同,
差别只来自**怎么用这个射频**:

- **手柄在游戏里是连续流**,摇杆每个连接事件都在传,11.25 毫秒一次,约每秒 89
  次,整局不停。三秒里它有两百多次机会,而且必须**全部**失败才掉线 —— 全程暴露。
- **鼠标是突发流**,BLE 鼠标靠 slave latency,不动就跳过连接事件。你用手柄打
  游戏时鼠标搁在一边基本不发包,丢无可丢。

所以「手柄死、鼠标活」**正是一个只咬连续流量的干扰源会预测的结果**,不是反证。
它真正排除掉的是「这台平板蓝牙栈整体坏了」(那样两个都得死),指向的是「某个
东西的强度刚好够杀死连续流、不够杀死突发流」。再叠一层:掉线只在**握着**时发生,
而人手对 2.4 GHz 有 10–20 dB 吸收,鼠标躺在桌上没这一层 —— 这直接对上了「玩
几分钟才断」。

### 一个「余量」模型,而不是单一真凶

把上面几条合起来,最省假设的解释不是「找到那个凶手」,而是**链路余量被几项各自
可生存的损耗叠加到临界**:

- 一项**平板专属**的基线余量损失(别的设备没有,所以只有这台出问题);
- 加上**握持吸收**(所有设备都有,但只有在基线已经吃紧时才压过临界);
- 作用在**连续流**上(所以咬手柄不咬鼠标)。

这个模型同时解释了三个约束:只有这台平板、只在握着玩时、只咬手柄。它也说明为什么
不该指望单个开关能修好 —— 要么补回那项平板专属的损失,要么给手柄留出更大的余量
(比如更长的监督超时,但那个参数由手柄定)。

### 更正:三个说重了或说错了的结论

- **RSSI −33 到 −39 dBm 排除不了「信号问题」**,两个漏洞:(一)RSSI 只量信号
  强度、**不量噪声底**,决定丢包的是信噪比,强信号 + 高噪声底照样丢;(二)这些
  RSSI 是**掉线之后**从广播包读的,那时手多半已离开手柄,而掉线发生在握着玩时,
  两个条件下链路预算可能差十几个 dB。**用错条件的数据排除了故障条件下的嫌疑。**
- **手柄固件不单独解释掉线。**同一个手柄在别的设备上不断,固件单方面站不住。
  本文档早先「要么等飞智改固件」是并列摆的无证据方向之一,不该显得像结论。
  (注意:这只撤回「固件导致**掉线**」;上一节「回连时机被手柄卡住」仍然成立。)
- **连接参数震荡不是扳机。**震荡 24 秒一次,掉线 5–10 分钟一次 —— 两次掉线之间
  手柄平安重协商了 12 到 25 回。若参数失配会直接杀链路,不可能容忍这么多回。
- **「重连后 1.5–3 秒才广播」推不出「失效不对称」。**如上一节所述,对称失效 +
  固件固定重启延迟同样能解释这个延迟。所以它**不能**用来给「ROM 后台扫描」或
  「环境干扰」这类对称干扰源降级 —— 排查中期我一度这么用过,是错的。

### 对照实验:换掉坞的电源线,掉线率降了近 60 倍

2026-08-24 晚,用户换掉了 USB-C 坞的电源线。这是一次意外的、但变量非常干净的
对照 —— **应用侧代码在前后完全相同**(所有射频争用修复在 08-23 15:42 前已全部
装机),手柄固件也是同一版。

| | 08-23 15:42 之后 | 08-24 晚 |
|---|---|---|
| 应用代码 | 与右侧**完全相同** | 同左 |
| 游戏时长 | 8 分钟 | **129 分钟** |
| 自发掉线 | **7 次** | **2 次** |
| 平均间隔 | 约 1.1 分钟 | 约 65 分钟 |

第二局 20:15–21:22 连续 **67 分钟零掉线**,这是整个排查里从未出现过的。

保留意见:08-23 那 8 分钟本身是一次「聚集」(08-24 也出现过 85 秒内两次的聚集),
拿聚集期比一整晚不完全公平。但两晚的应用代码相同这一点是硬的,所以**应用侧修复
不解释这次改善**;两晚之间用户动过的只有电源线(以及刷了一轮旧固件又刷回新固件,
净变化为零)。电源线是**已知的、唯一有意改动的变量**;未受控的还有射频环境本身
(邻居 WiFi 逐日不同)。

曾经怀疑过的一个混淆变量已被排除:**手柄电量**。08-24 两局之间手柄关机 17 分钟
但未充电,所以第二局开始时电量比第一局更低 —— 而第一局 62 分钟掉 2 次、第二局
67 分钟零掉线。电量单调下降,掉线却非单调,单调的变量解释不了非单调的结果。

干扰并未消失:掉线时的 BQR 里 `mUnusedAfhChannelCount` 仍稳定为 22,说明仍有
持续的宽带干扰源在吃信道。

### 关键改判:掉线不是「开关」,是停顿时长越线

08-24 加了一条心跳探针(手柄的数据包在 logcat 里逐条可见,`onNotify handle=21`,
约 11 ms 一条),只记录**间隔超过 400 ms** 的时刻。它抓到了以前完全看不见的东西:

```
20:38:31  停顿  742 ms   ← 恢复了
20:38:32  停顿  743 ms   ← 恢复了
21:21:39  停顿 2858 ms   ← 恢复了!距 3000 ms 判死线只差 142 ms
```

**那对 742/743 ms 是全部数据里信息量最大的一条。**把起止时刻还原出来:

```
20:38:30.663  停顿开始
20:38:31.405  恢复          停了 742 ms
20:38:31.518  又停          中间只正常了 113 ms
20:38:32.261  恢复          停了 743 ms
```

两次时长几乎一模一样,中间只放行 113 毫秒 —— 约 740 ms 占用、约 110 ms 释放,
周期约 855 ms。**干扰是随机的,不会连着两次都精确停 740 毫秒。这个形态是一台
占空比机器:有东西在按固定节奏把射频拿走。**

这条指向的方向和「噪声抬高底噪」完全不同 —— 是**射频被占用**,不是**信号被淹没**。
它还解释了一个别的假设解释不了的现象:**信号强度与掉线无关**(真掉线发生在
−72/−73 dBm,而人工断开时读到 −55/−56,两者都能断)—— 射频被拿走时,信号再强
也没用。

平板上有名有姓的周期性射频占用者有两个:ROM 的 `com.zte.distservice`(19 小时
开机里扫了 5 小时 42 分,约 29% 占空)与 WiFi 后台扫描(`wifi_scan_always_enabled=1`,
一次 2.4 GHz 全频段扫描典型几百毫秒到一秒多,且 WiFi 与蓝牙共用同一颗组合芯片)。
两者都是平板专属,都只咬连续流不碰空闲的鼠标。

**判别方法已就位**:采集里增加了扫描起止时刻的记录,下次出现停顿,看它是否与某次
扫描的窗口重合即可 —— 这是决定性的。两个假设的预测正好相反:噪声型会让
`mUnusedAfhChannelCount` 变化,射频占用型不会。

**链路会反复停顿,大多数自己缓过来。所谓「掉线」,只是某一次停顿越过了监督超时
那条线。**同一个机制、同一种现象,只是有的过线有的没过。

这推翻了本文档早先的「开关型失效」框架。那个框架来自一个采样偏差:**没越线的停顿
不产生任何日志**,样本里只剩越线的,于是看起来像是「完好到完好、瞬间归零」。

推论:**判死线的位置直接决定掉线率。**当前 `timeout=300`(3000 ms)是手柄自己
要求的,它会在连上后几秒内覆盖掉应用请求高优先级时设的 5000 ms(实测该设置约
维持 6.8 秒后被改回)。若能把监督超时保持在 5 秒,上面那次 2858 ms 的停顿连风险
都算不上。应用因此增加了定期重申高优先级的机制,见 `LOW_LATENCY_REFRESH_MS`。

诚实的保留:两次真掉线的**停顿实际有多长,无法得知** —— 链路在 3 秒整被判死,
之后就没有观测了。所以「5 秒超时能救回它们」是推断,不是已验证的结论。这个改动
的效果要靠后续「越过 3 秒但存活」的停顿计数来验证。

### 找到了控制器自己的黑匣子:BQR

排查后期才发现,链路监督超时会触发 **BQR(Bluetooth Quality Report)**,报告直接
打在 logcat 里(`BqrVsLsto`、`sendMindSyncEvent: bt_lsto_report`),**不需要
btsnoop**。它给出控制器第一手的现场记录:

```
mQualityReportId: Approaching LSTO(0x02)
mRssi: -73                     ← 游戏中的真实工作电平
mUnusedAfhChannelCount: 22     ← 被自适应跳频拉黑的信道数
mAfhSelectUnidealChannelCount: 0
mLsto: 4800                    ← 4800 × 0.625 ms = 3000 ms
```

两条重要的读法:

- **RSSI 在游戏中是 −72/−73 dBm,不是本文档早先写的 −35。**那些 −35 是掉线后
  从广播包读的,手已离开手柄。工作余量比原先声称的差了近 40 dB。
- **恒定字段不可信。**这份报告里 `mRetransmissionCount`、`mCrcErrorPackets`、
  `mNoRxCount`、`mCxmDenials` 全是 0 —— 一条刚经历三秒完全静默的链路不可能零重传,
  所以这些字段**没有被填充**,它们的 0 是「没数据」而非「没发生」。判据:**跨样本
  会变的字段才是真测量**(`mRssi`、`mAfhSelectUnidealChannelCount` 会变;
  `mUnusedAfhChannelCount` 恒为 22,存疑)。据此,早先用 `mCxmDenials: 0` 排除
  「WiFi/蓝牙抢天线」的做法**作废**。

### 探针的盲区,值得单独记一笔

心跳探针只记录「停顿」和「断开」。**手柄根本没连上时,它同样一片安静** —— 于是
「没有告警」和「一切正常」在数据上长得一模一样。08-24 晚就因此差点把「手柄关着的
45 分钟」误读成「链路极其稳定」。

凡是只在异常时输出的探针,都要配一个独立的「目标是否在线」的确认,否则沉默会被
当成健康。

### 分辨自发掉线与人工断开

统计掉线率时必须剔除人为断开,而两者在 `hciReason` 上**完全相同**(都是 0x08
监督超时 —— 关掉手柄同样是「对面不再发包」)。可靠的判据是**之后有没有自动接回**:

- 自发掉线:4 秒内自己接回(实测 3.9 s、4.1 s);
- 人工关机:不会接回,因为手柄没在广播。
